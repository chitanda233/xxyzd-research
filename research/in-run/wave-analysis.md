# 第一章 15 波：局内节奏还原

> 研究对象：APK 客户端约 1.0.16 / versionCode 40。本文只写策划结论；字段与 RVA 证据集中在文末和 `evidence/native-key-paths.md`。

## 结论先行

第一章不是“15 波等价循环”，也不能再简单概括成“4+1 / 4+1 / 4+1 三个相同硬节点”。实际运行用的是 `ChapterWave_Waves` 的 100101～100115；其中只有第 10、15 波开启“必须击杀精英/Boss 才能继续”的硬门槛，第 5 波没有这个门槛。

更准确的节奏是：

- 第 1～4 波：快速建立操作与基础 Build，刷新脚本短、怪型少，约每 15 秒进入下一段。
- 第 5 波：第一次明显的脚本化密度峰。一次波次里拆成 16 条刷新任务，属于“第一幕高潮/压力测试”，但不是精英击杀锁。
- 第 6～9 波：继续引入组合、随机小怪组和更复杂的刷新方式；第 9 波出现明显更高的攻击修正。
- 第 10 波：真正的精英硬门槛。配置中出现 Type=201 的 310008，并且 `StopByEliteOrBossKilled=1`。native 还显示特殊目标清零后会清掉尚未执行的刷怪计划，因此这一波的推进核心是“解决关键目标”，而不是机械等所有后续脚本自然播完。
- 第 11～14 波：第三阶段的密度和混合刷新继续加重，金币预算也明显上升。
- 第 15 波：Boss 340002（Type=3，HP 40000）进入，且同样是击杀硬门槛。Boss 死亡会终止尚未执行的怪物创建计划。刷新起点约为战斗时间 345 秒，因此 Boss 前的有效战斗时间轴约 5 分 45 秒；三选一、波间 UI 和硬门槛等待会让真实墙钟时间更长。

所以第一章的节奏设计不是“每 5 波一个同构节点”，而是 **第一次压力峰（W5）→ 精英校验（W10）→ Boss 校验（W15）**，三个节点承担的职责不同。

## 为什么经验与波次是同一条时间轴

`Exp_exp.waveExp` 前 15 级阈值为：

`200, 750, 1350, 1950, 2650, 3450, 4250, 5200, 6200, 7300, 8500, 9700, 11100, 12800, 14800`

这恰好逐项等于第一章 `WaveAllExp` 的累计值。不是“趋势相近”，而是 15 个点逐个完全相等。因此第一章有很强的“完整吃完一波经验 ≈ 推进一个等级”的设计意图。

native 实现进一步说明它不是靠每种怪固定经验自然碰巧凑出来的。新波开始时，`WaterfallBattleManager.InitNewWaveData` 先统计该波用于分摊经验的计数/权重，随后直接执行近似：

```
_perExp = max(1, WaveAllExp / _expCount)
```

实际掉落再乘怪物自身的经验权重，并用 `_addExp` 做累计/尾差控制。因此 **WaveAllExp 是这一波的总预算，怪物 expWeight 更像预算分配系数，而不是独立决定整局经验曲线的绝对经验值。**

这给策划带来一个非常重要的自由度：可以大幅改变一波的怪物数量和强弱组合，同时保持“本波大约升一次”的成长节奏不漂移。第 15 波只有 Boss 也能拿到完整的 2000 波经验预算；第 5、12 波怪物更密，也不会因为怪多而把升级节奏冲爆。

## 升级并非随杀怪即时打断，而是波末收束

第一章 `WaitUpLevel=1`。在 Waterfall 模式里，还能看到专门的 `_needUpLevelCount`、`curWaveUpLevelCount` 和 `WaveEndUpLevelProgressState`。

`OnProgressFinish` 的 native 路径会先检查场上是否还有装备/经验掉落。如果经验仍在地上，会调用 `DropMgr.AbsorbAll`；等经验动画进入可升级状态后，再根据 `_needUpLevelCount` 调用 `QueueSelectSkill`，进入选技能状态。一次选择完成后，`DelUpLevel` 会把待处理升级数减 1，并把本波已处理升级数加 1。

因此第一章更接近：

**打一波 → 收束场上掉落 → 结算本波经验 → 触发局内选择 → 下一波**

而不是传统幸存者游戏那种“任何时刻经验条满就暂停战斗”。这让关卡策划可以把三选一当成波次标点使用：玩家在下一波开始前做一次明确决策，随后立刻用新 Build 面对下一段压力。

严格说，代码支持“一波积压多次升级”的队列，所以异常加成或额外经验条件下不一定永远只有一次选择；但在第一章基础配置中，每波总经验与下一等级阈值逐项对齐，基准节奏显然按“一波约一升”校准。

## 硬门槛不是“清场门槛”，而是关键目标门槛

W10/W15 的 native 路径比配置字段本身更有解释力。`EnemyDieSpecialLogic` 只有在当前波开启 `StopByEliteOrBossKilled` 时才进入特殊处理，并且只把 Monster Type 201 与 Type 3 计入特殊目标。每死一个特殊目标，`_remainSpecialMonsterCount` 减 1；当它归零后，系统调用 `EnemySpecialDie`，随后更新当前 mission，并执行 `ClearMonsterCreateData`。

策划上这意味着：**硬门槛的真正验收对象是精英/Boss，而不是“把这一波所有普通怪和未来刷新批次全部清干净”。** 关键目标死亡后，尚未执行的刷怪计划会被截断；已经在场的普通怪仍可能参与最后清理，但它们不再决定这波是否继续生成压力。

这让 W10/W15 的体验更集中：杂兵负责制造走位和火力干扰，精英/Boss 才是必须解决的主目标。玩家不会因为关键目标已经打掉，却还要无意义地等待剩余定时刷怪脚本播完，从而破坏高潮后的收束感。

## 三个阶段的策划意义

第一阶段的核心不是杀伤玩家，而是快速建立“操作—掉经验—选强化”的反馈。W1～W4 采用明确的位置组脚本，刷新起点几乎就是 0/15/30/45 秒的教学式刻度。到了 W5，刷新方式突然从单一位置组变成 16 条脚本任务，这是第一次通过密度而不是纯数值告诉玩家“刚才拿到的 Build 要开始工作了”。

第二阶段把随机组、间隔刷新和更强中型怪逐渐加进来，到 W10 用真正精英硬门槛结束。这里的设计价值是把“活下来”变成“能不能在合理时间内解决关键目标”；即使玩家擅长躲避，Build 输出不足也会在精英节点暴露。

第三阶段继续提高 HP 倍率、攻击修正、刷新混合度和金币预算，最后 W15 用 HP 40000 的 Boss 收口。Boss 波 HP 倍率又跳到 11，且必须击杀才能推进，属于明确的终局 Build 验收。

## W5、W10、W15 的性质必须区分

旧分析曾根据 `ChapterWave_Sections` 把 5/10/15 都写成 `StopByEliteOrBossKilled=1`。但第一章实际引用的是 `waveId=100100`，对应 `ChapterWave_Waves` 的 100101～100115；这里 W5 的 Stop 为 0，W10/W15 才为 1。

这说明 `ChapterWave_Sections` 不能脱离实际章节引用直接当最终运行数据。后续报告以“章节指向的 Waves + Waterfall Mission + native 状态机”作为主证据链，Sections 仅作为旁证/历史或通用结构参考。

## 怪物角色的可确认锚点

不需要在策划正文列完整实体表，但几个锚点有助于理解压力变化：

- 330006：基础小怪，HP 150，expWeight 1。
- 320017/320019/320021/320022：中型普通怪，HP 约 800～1200，expWeight 3。
- 320005/320035：更重的普通怪，HP 2350，expWeight 6。
- 310008：Type 201，HP 7000，显式血条，expWeight 6；W10 的精英锚点。
- 340002：Type 3，HP 40000，Boss AI，expWeight 15；W15 最终 Boss。

这再次说明经验权重和战斗威胁大体同向：更重目标分走更大比例的波经验预算，使击杀重要目标同时带来更明确的成长回报。
