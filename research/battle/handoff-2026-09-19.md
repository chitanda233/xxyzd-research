## 三、第一章 15 波：已经可以当作正式结论的部分

第一章节奏不是“5/10/15 波都是同一种硬节点”，而是：

**1～4 波铺垫 → 第 5 波第一次明显高潮/特殊事件 → 6～9 波继续抬压 → 第 10 波第一处真正精英死亡锁 → 11～14 波终盘抬压 → 第 15 波 Boss 死亡锁。**

已形成配置、实体类型、native 逻辑三方闭环：

- 第 5 波：
  - 有特殊 UI / 事件节奏；
  - `StopByEliteOrBossKilled = 0`；
  - 因此不能写成和 10/15 波同性质的“必须击杀后推进”。
- 第 10 波：
  - `StopByEliteOrBossKilled = 1`；
  - 实体 310008 为 Type 201；
  - `EnemyDieSpecialLogic` 明确把 Type 201 作为特殊死亡处理对象；
  - 可正式写成精英死亡硬门槛。
- 第 15 波：
  - `StopByEliteOrBossKilled = 1`；
  - 实体 340002 为 Type 3；
  - 同一死亡逻辑明确处理 Type 3；
  - 可正式写成最终 Boss 死亡硬门槛。

第一章 15 波的具体开始时间、怪物数量/组合、批次与名义持续时间已经整理在 `wave-analysis.md`，不要重新手工统计。

### 节奏层最重要的设计结论

1. 第一章刷怪压力不是线性递增，而是“抬高—回落—再抬高”。
2. 第 8、11、12 波负责数量压力峰值，第 9、13 波明显承担强节点前的缓冲。
3. 第 5 波是第一次明显高潮，但性质是节奏事件，不是死亡锁。
4. 第 10 波才是第一次真正的生存/输出硬校验。
5. 第 15 波以单 Boss 收束。

## 四、经验与波末升级：已经坐实

第一章每波 `WaveAllExp`：

`200, 550, 600, 600, 700, 800, 800, 950, 1000, 1100, 1200, 1200, 1400, 1700, 2000`

与 `Exp_exp.waveExp` 相邻累计阈值差逐项对应，因此：

**完整一波的经验预算 = 一个等级的经验预算。**

进一步的 native 已经证明，这不是“怪物静态经验碰巧相加等于一波升级”。

`WaterfallBattleManager` 会在每波开始根据 `WaveAllExp` 和本波怪物结构计算经验分配基准，击杀时再动态发放并在尾部做差额修正，保证整波经验预算闭合。因此正确的策划理解是：

**先规定一波必须给多少总经验，再把这份预算分摊到该波怪物掉落上。**

### 波末升级顺序

`OnProgressFinish` 已确认：

1. 检查场上装备/经验掉落；
2. 必要时 `AbsorbAll`；
3. 等经验动画进入可升级状态；
4. 再进入 `QueueSelectSkill`；
5. 三选一结束后继续波末流程，而不是战斗中途跨经验线就立即弹窗。

因此 `WaitUpLevel = 1` 可以正式描述为：

**经验仍由战斗产生，但升级决策被同步到波末处理，从而把“战斗阶段”和“Build 决策阶段”切开。**

### 一波跨多级

波末升级状态机已经可还原为行为状态：

`0 Idle → 1 Queued → 2 Selecting → 3 FinishedPendingContinue → 0`

关键字段/逻辑：

- `_needUpLevelCount`：待处理升级次数。
- `curWaveUpLevelCount`：本波已完成升级次数。
- 一次三选一结束只消费 1 个 `_needUpLevelCount`。
- 如果还有升级债务，会再次进入选择，而不是多级合并成一次选择。

因此“一波累计多个等级”已经闭环：**多级 = 连续多次三选一。**

## 五、三选一动态权重：已经可以正式写进策划报告的部分

当前可以正式确认：

**三选一不是独立均匀随机，而是会根据玩家已经学习的 skillType 对后续同类技能进行持续增权，让 Build 软收敛。**

### 精确公式

`Skill_SkillTypeWeight` 主流配置：

- AddWeightPerSkill = 50
- AddWeightMax = 500

native `GetDeltaWeightPercent` + `WeightRandomData.PracticalWeight` 已经把公式闭环：

```text
delta = min(同类型已学习数量 × 0.5, 5.0)
effectiveWeight = baseWeight × (1 + delta)
```

对应：

- 0 个同类：1.0×基础权重
- 1 个同类：1.5×
- 2 个同类：2.0×
- 3 个同类：2.5×
- ...
- 10 个及以上：6.0×封顶

注意：这是“有效权重倍数”，不是最终概率倍数；最终概率仍取决于当次合法候选池总权重。

### Build 收敛链路

已经确认：

`学习/移除技能 → skillType 学习数量变化 → GetDeltaWeightPercent → AdjustWeightsForSkillGroup → 后续抽取有效权重变化`

所以报告里可以写：

**玩家越早在一个类型上投入，后面的三选一越倾向继续提供这个 Build 的发展方向，但不是硬锁池。**

### 候选不是一锅抽三张

已经确认至少存在两层结构：

1. 先按“已学 / 可学 / 一星 / 父子升级关系”等条件构造多个合法子池；
2. `HeroSkillCreator.GetRandomSkills` 先用池级权重决定从哪个子池开始；
3. 每个 `WeightRandom` 子池内部再按实时有效权重做无放回抽样；
4. 同一次抽取中已进入 result 的技能 ID 会被排除，避免同批重复；
5. 父技能型候选会进一步解析为具体合法子技能。

因此最终三选一是：

**池级随机 + 子池内动态加权 + 合法性过滤 + 同批去重。**

### NewPlayerBoost

`BoostWeightByPercent / RevertWeightBoost` 已经定位到 `SinglePlayerSkillCreator.GetNormalSkill` 的 `_newPlayerBoostRecords`。

它是另一套独立机制：

- Build 收敛增权：持续、由已学习 skillType 驱动；
- NewPlayerBoost：临时、指定技能增权、抽完后 Revert。

不要把两者混成同一种机制，也不要把 NewPlayerBoost 写成普通 Build 的“保底”。

目标是把“名义 43s / 30s”等变成“什么条件会延长，什么时候真正解锁下一阶段”。

### B. AdjustWeightsForSkillGroup 的 HotFix 实体方法体

当前 ARM64 中 `AdjustWeightsForSkillGroup` 是 HotFix 分发壳，真正热更方法体没有静态展开。

已经能证明：

- skillType count 会产生精确 delta；
- 随机器条目支持 delta；
- PracticalWeight 真正使用 delta。

但如果想做到 implementation 级百分之百闭环，还需要补：

**某个 skillType 的 delta 最终覆盖组内哪些 WeightRandom 条目。**

这可能需要：

- 热更 DLL/IL 进一步恢复；
- 或运行时 hook / 日志；
- 或从构建后的分组数据反推。

### C. 三个候选位的子池语义

`HeroSkillCreator.GetRandomSkills` 已证明“池级起点随机 → 子池逐个补满”，但还没有完全映射：

- randoms[0]/[1]/[...] 分别是什么语义池；
- skillWeights[] 在具体模式下的数值；
- 三个候选位置是否存在固定优先级；
- 已学技能 / 新技能 / 升级技能各自的占位关系。

这是下一步三选一最有价值的深挖点。

### D. NewPlayerBoost 的触发条件

调用方已经找到，但尚未把触发条件对应到具体：

- 新手第几局/第几章；
- 哪些技能；
- 加多少；
- 哪个配置控制。

这属于次优先级，不要放在 A/B/C 前面。
