# 第一章 15 波节奏还原

> 研究版本：客户端约 1.0.16 / versionCode 40。本文目标是把第一章 78 条底层刷怪指令压缩成策划可读的 15 波节奏，并把“配置事实”“native 已证实行为”“仍需补证的推断”分开。

## 一、当前可以直接下的策划结论

第一章并不是“5/10/15 三个完全同性质的硬节点”。`ChapterWave_Waves` 明确显示：第 5 波的 `StopByEliteOrBossKilled=0`，而第 10、15 波为 1。因此更准确的节奏结构是：

**W1–W4 建立基础压力 → W5 第一次明显高潮/事件节点，但不构成击杀锁 → W6–W9 二次抬压 → W10 第一次真正击杀硬门槛 → W11–W14 终盘持续抬压 → W15 最终 Boss/硬门槛。**

第一章每波 `WaveAllExp` 为：

`200 / 550 / 600 / 600 / 700 / 800 / 800 / 950 / 1000 / 1100 / 1200 / 1200 / 1400 / 1700 / 2000`

与 `Exp_exp.waveExp` 的累计等级阈值差逐波吻合。换句话说，这不是“经验大致够升级”，而是明显按 **完整打一波 ≈ 恰好推进一级** 的节奏设计。第一章同时开启 `WaitUpLevel=1`，再结合 `WaterfallBattleManager` 中的波末升级状态机，可以把“每波一次成长选择”视为第一章核心节拍，而不是偶然结果。

## 三、推进规则：定时推进与击杀门槛不是一回事

`WaterfallBattleManager` 中存在独立的 `CheckStopByEliteOrBossKilled` 与 `CheckGoNextMission`，说明“是否允许继续推进”并不是简单按 Mission 时间用完就切下一波。结合配置，第一章至少有两类节点：

- **普通波与 W5：** `StopByEliteOrBossKilled=0`，因此不会因为“精英/Boss 尚未击杀”这一条件强制锁死下一波。W5 仍可有特殊 UI、特殊刷怪或事件表现，但其逻辑性质和 W10/W15 不同。
- **W10/W15：** `StopByEliteOrBossKilled=1`，这两波明确属于“必须完成精英/Boss 击杀条件才能继续”的硬门槛。配置时间只决定刷怪和事件何时出现，不保证玩家能在固定时间点离开该波。

这意味着第一章节奏不是纯时间轴 survival，而是 **大部分波按时间轴推进，关键节点转为击杀完成度控制** 的混合结构。

## 四、波末升级：经验来自战斗，但三选一被波末状态机统一接管

native 证据已经能把这一点坐实到较高置信度。经验仍然通过怪物/掉落与 `AddUserExp` 进入战斗数据，但 `WaterfallBattleManager.OnProgressFinish` 在波末会检查掉落经验是否尚未吸收、经验动画是否仍在处理、当前是否还能升级；必要时先执行全吸收，再进入 `QueueSelectSkill`。同时类内存在：

- `QueueSelectSkill`
- `WaveModelLevelUp`
- `MarkWaveEndSelectSkillFinished`
- `TryContinueWaveEndUpLevelAfterSelection`
- `TryResumeWaveEndUpLevelProgress`
- `CanRunUpLevelProgress`
- `OnProgressFinish`

其中 `MarkWaveEndSelectSkillFinished`、`TryContinueWaveEndUpLevelAfterSelection`、`TryResumeWaveEndUpLevelProgress` 明确表明：**升级选择并不是简单“经验条一满立刻弹窗”，而是波末流程中的一个可暂停、可恢复、可连续消费的状态。**

因此第一章的更合理还原是：

**怪物死亡/经验掉落 → 波内累计经验 → 波末吸收/经验动画处理 → 判断可升级次数 → 排队三选一 → 完成一次选择 → 若仍有待处理升级则继续下一次 → 全部处理完成后才恢复波末推进。**

这也解释了 `_needUpLevelCount` 与 `curWaveUpLevelCount` 的存在：如果某一波因为额外经验、补偿或特殊来源跨过多个等级阈值，系统不是丢掉额外等级，而是把多次升级作为波末队列连续处理。

### 证据强度

**已坐实：**
1. 第一章 W10/W15 是击杀硬门槛，W5 不是。
2. 第一章每波经验预算与逐级经验差严格对齐，“一波一级”是强设计意图。
3. 波末存在升级选择状态机，并且会等待经验掉落/经验动画处理。
4. 波末升级选择完成后存在“继续处理剩余升级”的恢复逻辑。

**高概率、仍建议补一层伪代码：**
1. `_needUpLevelCount` 的精确加减时机与 `curWaveUpLevelCount` 的重置边界。
2. 一波多级时每次三选一之间是否重新计算技能池/权重（从整体代码结构看很可能会，但应以调用链为准）。
3. W5 的特殊 UI/事件具体对应哪种精英表现，当前应写成“第一次高潮/事件节点”，不要写成与 W10 相同的“硬精英门”。

## 五、策划视角的第一章核心循环

第一章可以简化成：

**进入战斗 → 20~若干秒一轮的刷怪压力 → 收集经验 → 波末统一结算经验 → 基本每波一次三选一成长 → 下一波在已有 Build 上抬压 → W5 给第一次明显高潮 → W10 用击杀硬门槛检验中期 Build → W11–14 加速终盘成型 → W15 最终 Boss/硬门槛 → 结算。**

所以它的核心不是“15 个独立关卡”，而是 **15 个短战斗段落 + 14~15 次局内成长反馈** 拼成的一条 Build 成型曲线。波次是战斗节奏单位，同时也是成长选择的天然节拍器。

## 六、后续还应继续补的证据

下一轮最值得深挖的是：

1. 把第一章出现的实体 ID 映射为普通怪/精英/Boss的策划命名与可视特征。
2. 对 `CheckStopByEliteOrBossKilled` 做伪代码级还原，明确它检查的是“存活数量”“特殊怪计数”还是某个 Boss 标记。
3. 对 `QueueSelectSkill → MarkWaveEndSelectSkillFinished → TryContinueWaveEndUpLevelAfterSelection` 做完整状态迁移图。
4. 如有实机录屏，可把配置秒点与屏幕时间对齐，用来区分“配置绝对时间”“波内相对时间”和“暂停后的实际时间”。
