1. 一局游戏的主循环

当前最稳妥的还原是：进入章节或模式 → 加载波次/地图与怪物 → 单位自动进行移动、攻击与受击结算 → 玩家在成长节点从技能池中获得或升级技能 → 继续处理更高强度波次 → 获得局内掉落与关卡奖励 → 把资源带回局外成长系统。

① 进入关卡章节、Mission、地图与模式参数
② 生成敌人波次表、刷新器、怪物池
③ 自动战斗实体行为、Buff、受击与伤害
④ 选择成长技能组、权重、前置与升级链
⑤ 波次推进更换刷怪配置并继续战斗
⑥ 结算掉落、首通/完成奖励与局外资源

这条链不是只根据文件名拼出来的。仓库交接说明本身建议优先追踪 WaterfallBattleManager → 波次配置 → 刷怪配置、HeroSkillCreator / NormalSkillCreator 的选技能逻辑，再追 CharacterComponentOnHit 的伤害路径；系统索引也把这些代码入口分别归到关卡刷怪、随机选牌和伤害行为三个模块。

证据边界：目前没有实际运行客户端，因此“何时弹出选技能”“击杀经验如何累计”“Boss 波具体切换时机”等动态时序仍需要运行验证。页面描述的是静态结构能够支持的玩法闭环，不把未验证时序写成事实。

2. 章节、波次与刷怪

主线便捷数据 chapters-readable.json 不只是章节标题表，而是直接把章节与战斗参数连在一起。第一条记录已经同时出现 waveNum=15、waveId=100100、地图样式、预览怪物、推荐技能、技能类型、宝箱类型、首通奖励和完成奖励。这说明“章节”更像一层战斗容器：它引用具体波次，并附带成长、掉落和展示信息。

3. 单位战斗：实体、Buff 与受击

伤害与怪物行为模块的主要代码入口是 CharacterComponentOnHit、CharacterComponentBuff 和 EntityMonster。角色/怪物图鉴表又能看到实体与技能列表之间的直接关联，例如怪物记录包含 characterid、类型、标签与 Skillid。这支持一种典型的数据驱动战斗架构：实体配置负责“是谁”，技能/Buff 配置负责“会什么”，Component 层负责运行时的受击、状态和行为。

目前不应该在网页上凭字段名提前写死完整伤害公式。原因是实际伤害很可能跨实体属性、Buff、技能 Mod、目标标签及原生函数调用，且间接调用尚未全部解析。所以本页先把“计算链入口”画清楚，后续再单独建立伤害专题。

4. 局内随机技能构筑

这一块是目前最值得继续深挖的核心。仓库不是只有一张 Skill_Main：系统索引里有 42 张技能与随机选牌相关可读表，同时代码侧存在 HeroSkillCreator、SinglePlayerSkillCreator、NormalSkillCreator、HeroComponentRandomSkill 和通用的 WeightRandom。因此更合理的理解是“多层过滤 + 分组 + 加权随机 + 升级/依赖关系”，而不是所有技能平铺后等概率抽取。

4.1 技能池与技能组

SkillGroup_BaseGroupRoom 当前可读到 17 个 Event，每条都有 GetID 与 Weight。这已经足以证明房间基础技能组存在显式权重层。具体 GetID 最终落到哪一类技能/事件，需要继续沿引用关系核对，但网页把它作为“基础候选池”而不是直接等同于 Skill_Main。

层关键字段/类作用判断
候选技能Skill_Main 1,184 条记录技能类型、星级、前置、升级、互斥、目标、触发器、图标与文案键等
技能组SkillGroup_BaseGroupRoom按 Event/GetID/Weight 组织候选项
类型权重Skill_SkillTypeWeight按类型记录递增权重与最大附加权重
随机执行HeroComponentRandomSkill / WeightRandom代码侧存在专门的随机技能组件与加权随机入口

4.2 权重不是固定值

Skill_SkillTypeWeight 中多个类型都出现 AddWeightPerSkill=50、AddWeightMax=500。仅凭这张表还不能断言它就是“连续没抽到某类就加权”的保底，但可以确认系统为技能类型预留了“随技能数量/状态增加权重并设置上限”的参数结构。真正的累加条件需要继续在 WeightRandom 及调用者的原生实现里核对。

4.3 Skill_Main 自带构筑关系

每条 Skill_Main 都不仅有名字和说明，还可能带 UpgradeSkillId、UnlockUpgradeNeddSkill、PreSkillIds、RejectSkills、NeedSkills、CoverSkill、NextSkill、BanSkillS、RepeatSkills、SuperNeedSkill 等关系字段。这意味着完整“卡牌页”应该展示技能网络，而不能只做卡面列表。当前技能数据库页先把这些原字段完整保留，下一步可以基于它们生成升级树与互斥关系图。

另外 Skillss_Ring 能看到诸如 RingSlowBullet、RingAddBuffContinue、RingDamageContinue、RingCombine 等运行类名，并带半径、BuffId、伤害、间隔、阵营和目标类型参数。这提供了技能效果实现的一类具体证据：部分技能不是只改属性，而是创建范围逻辑并持续对范围内目标施加效果。

5. 掉落与关卡结算

奖励模块同时存在 MainDropManager、DropMgr 与 Item_drop，而章节层又含首通、完成等奖励字段，因此“战斗过程中掉落”和“关卡结束奖励”应分开理解。Item_drop 中的 reward 字符串还能看到大量物品及数值/权重组合，后续可以进一步拆成独立的掉落概率与资源流专题。

6. 同一战斗骨架上的模式簇

主线 / Chapter

配置证据

章节直接引用波次、地图、预览怪物、推荐技能和奖励，是目前最完整的“局内入口容器”。

Room / Tower

配置证据

存在独立 Mission 配置，含房间池、门、基础 Mission 与倍率等参数。

Waterfall / Survival

代码入口

WaterfallBattleManager 与 BaseSurvivalBattleManager 表明有不同战斗管理分支。

多人 / Boss

代码入口

WaterfallMultiBattleManager、GuildBossBattleManager、WorldBossBattleManager 暗示战斗骨架还被多人、公会 Boss 和世界 Boss 复用。

7. 当前最值得继续验证的五件事

  1. 升级资源/经验具体如何触发 HeroComponentRandomSkill，每次提供几个候选项。
  2. AddWeightPerSkill 的实际累加条件与清零时点，是否构成某种“类型平衡/防脸黑”机制。
  3. Skill_Main 的前置、互斥、Cover、Next、SuperNeed 等字段在筛选流程中的先后顺序。
  4. 章节 waveId 到具体怪物刷新表的完整引用链，以及 Boss 波/精英波判定。
  5. 结算奖励、战中掉落、宝箱与局外成长之间的资源闭环。

主要证据入口：gameplay/chapters-readable.json、gameplay/skills-readable.json、gameplay/systems-index.json、restored/configs/tables/*、restored/code/native-evidence/*。
